# BlaBlind — Architecture Analysis & Feature Proposals

_Date: 2026-07-12 — Scope: full application (game SPA, member area, admin, PocketBase backend, infra) — Follow-up to [REVIEW-2026-06-26.md](./REVIEW-2026-06-26.md)._

---

## 1. State of the architecture

### What works well (keep as-is)

- **Clear macro-structure.** One Astro shell, three Vue SPAs with their own routers and composables (`src/game`, `src/client`, `src/admin`), a PocketBase backend with versioned migrations and JSVM hooks. Responsibilities are easy to locate.
- **The autonomous-mode reconciler is the best pattern in the codebase.** `src/game/autonomous.ts` is a pure, level-triggered decision function (`AutonomousSnapshot → AutonomousAction`), executed by the host client with idempotent writes, crash-repair branches and unit tests. Host handoff and SSE reconnects recover mid-phase for free. This pattern should be the template for any future game-flow logic.
- **Server-side fixes for real concurrency problems.** The atomic skip-vote endpoint (`pb_hooks/skip_vote.pb.js`, transaction-serialized) and server-side host election (`host_election.pb.js`) correctly moved race-prone logic out of the clients.
- **Realtime robustness discipline.** `PB_CONNECT` reloads, `requestKey: null` on concurrent loads, double-insert guards, dedup of the solved animation — the lessons of the 2026-06 review were absorbed and are consistently applied across composables.
- **Deployment is simple and reproducible** (GitHub Actions → jota-one/infra, PB serving the built app from `pb_public`).

### Structural weaknesses

The rest of this document details four architectural problems, in priority order, then feature proposals.

## 2. Architectural improvements

### 2.1 Security: the gameplay collections are fully open (priority 1)

Current API rules (verified in the live schema):

| Collection | list | view | create | update | delete |
|---|---|---|---|---|---|
| `sessions` | public | public | public | **public** | **public** |
| `players` | public | public | public | **public** | secret param |
| `tracks` | public | public | public | **public** | **public** |
| `buzzes` | public | public | public | **public** | **public** |
| `answer_votes` | public | public | public | locked | locked |

Anyone with the PB URL can: delete any session or track, set themselves `host`, mark any buzz `correct`, rewrite `session.settings`, update another player's `ready`/`name`, or flood `buzzes`. Guest play makes `@request.auth` unusable, but the app **already has the solution in place**: the per-player `secret` (issued at join, stored in localStorage, already required for player deletion).

Recommended path, incremental:

1. **Generalize the secret as a write capability.** Route gameplay mutations through custom PB endpoints (the `skip-vote` endpoint is the template): `buzz`, `vote`, `validate`, `advance`, `session-update`. Each verifies `playerId + secret` and role (host-only for session updates, validator-only for buzz validation). Client changes are localized in the composables — components already call composable functions, not PB directly (except Room.vue, see 2.2).
2. **Close the answer leak** (already in ROADMAP). `tracks` is publicly readable with `expand: video`, so title/artist of the unrevealed current track — and typed answers in `buzzes.answer` — are one `curl` away. Since PB rules can't hide fields conditionally, serve the current track through a hook endpoint that strips `video`/`answer` until `solved_by`/`skip_revealed`/`phase === 'voting'`, and stop expanding `video` on queued/playing tracks client-side. This is the single change with the highest cheat-prevention value, and it matters more now that autonomous mode makes every player a guesser.
3. **Votes hardening**: `answer_votes.createRule` is public — add a hook validating that `voter` matches the secret and that the buzz belongs to the session the voter is in.
4. Keep the favorites server-side validation hook (already spec'd in ROADMAP).

None of this requires accounts for players; it only requires the client to send what it already possesses.

### 2.2 Room.vue is a 2 100-line monolith

`src/game/views/Room.vue` holds the lobby, playback layers, buzz zone, validator panel, three tabs with swipe logic, seven modals, the menu drawer, orphan-track flow, settings editing, reset, roles handover, drag & drop, duplicate detection, and the advance/skip orchestration. Symptoms: every feature lands here (the file grew ~400 lines per release), watchers interact non-obviously (five separate watchers touch `pausedByDuration`/`clearPlaybackTimer`), and it directly issues ~25 raw `pb.collection(...)` writes that bypass the composables.

Suggested split — extraction only, no behavior change, one PR per line:

| Extract | Contents |
|---|---|
| `components/RoomLobby.vue` | waiting-phase roster, ready/launch |
| `components/PlaybackCard.vue` | the 3-layer video/warm-up/UI container |
| `components/BuzzZone.vue` + `ValidatorPanel.vue` | classic-mode buzz + validation (mirrors the existing `AutonomousPanel.vue`, which proved the pattern) |
| `components/RoomTabs.vue` | tabs + swipe + track lists + ranking |
| `components/RoomMenus.vue` | drawer + roles/participants/settings/reset modals |
| `composables/useGameFlow.ts` | `advanceFrom`, `startTrack`, skip-vote watcher, orphan-track flow, playback-duration timer — the actual game orchestration, currently interleaved with UI state |
| `composables/useRoomRoles.ts` | host/DJ propose/approve/reject, claim |

Second, **move the raw PB writes into the composables** (`useTracks`, `useSession`…). That is also the precondition for the endpoint migration in 2.1 — one call site per mutation instead of scattered `pb.collection('tracks').update(...)`.

### 2.3 Typing: `any` everywhere at the data boundary

27 files use `any` for PB records (`session: any`, `tracks = ref<any[]>([])`, `props.currentPlayer: any`). The schema is stable and versioned in migrations — this is cheap to fix and pays off immediately in a codebase where fields like `skip_revealed`, `phase`, `started_at` carry the whole game state machine.

- Add `src/types/records.ts` with `SessionRecord`, `PlayerRecord`, `TrackRecord`, `BuzzRecord`, `AnswerVoteRecord`, `PlaylistRecord`, `FavoriteRecord` (or generate them with `pocketbase-typegen` against `pb_data/data.db`).
- Type the composable returns and component props first (the `defineProps<Props>()` convention is already the house rule); leave admin views for last.
- Typo-level bugs this would catch today: any misspelling of `skip_revealed`/`solved_by` in the five watchers of Room.vue would currently fail silently.

### 2.4 The host's browser is the game server

Phase transitions, timers, auto-advance and the autonomous reconciler all run in the elected host's tab. Mitigations exist (server host election, level-triggered reconciler, wall-clock recheck), but: a backgrounded/throttled host phone stalls the game for everyone, and the buzz-window timer is per-client wall-clock (a pause during the excerpt shortens the effective window — known ROADMAP item).

Two-step plan, aligned with work already planned:

1. **Short term (pure client, fixes the pause-aware window):** derive the window deadline from server timestamps instead of local `setTimeout` — `tracks.started_at` already snapshots the server-side start. Add an accumulated `paused_ms` on the track (host writes on pause/resume); every client computes `deadline = started_at + duration + paused_ms` and renders the same countdown. The host timer becomes a display-driven trigger, not the source of truth.
2. **Medium term (rides the Web Push work):** the ROADMAP already commits to a **custom Go PocketBase build** for Web Push. Once that exists, move the autonomous reconciler server-side: `computeNextAction` is already a pure function with a serializable snapshot — port it to Go (or run it via a `cronAdd`-style ticker + record hooks) and drop the host-client dependency entirely. The unit tests in `tests/unit/autonomous.test.ts` become the porting spec.

### 2.5 Smaller items

- **Dead dependencies:** `chart.js`, `pdfmake`, `vue3-markdown` have zero imports under `src/` — remove (`pdfmake` also drags the SSR `noExternal`/`__dirname` workarounds risk for nothing). `vitest` is installed but `test:unit` runs bare `node --experimental-strip-types`; either adopt vitest as the runner or drop the dep.
- **README drift:** says Astro 6 (now 7), lists 4 collections (now 12+), doesn't mention IRL/autonomous modes, playlists, favorites, member area. Worth a refresh since it's the onboarding surface.
- **Test coverage is thin where regressions actually happened:** the ROADMAP history is full of concurrency fixes (double skip, double score, reconnection). Unit-test candidates with high value and no infra needs: `useBuzzes.buzzBlockReason` matrix, `canAddTrack`/`canDeleteTrack` equity math, `skipVotesNeeded`, `playerRatio` ranking. E2E: an IRL-mode spec (DJ handover + verbal buzz) is the biggest untested flow.
- **Invidious fragility:** the search proxy already does multi-instance fallback + LRU cache, good. Two cheap upgrades: persist successful results into the existing `videos` collection as a first-tier search source (local catalog search already exists in `TrackSearch`), and make the instance list configurable via env so a dead-instance rotation doesn't need a deploy.
- **Heartbeat write amplification:** every player heartbeat (15 s) is a `players` update that fans out over SSE to all clients **and** runs the host-election hook (a session fetch + filtered player query). Fine at current scale; if sessions grow past ~20 players, batch it (single `last_seen` endpoint, hook early-exits when the host is online — the query can be skipped by checking the host record first).

## 3. Feature proposals

Ordered by (value ÷ effort), taking the existing ROADMAP into account — items already planned there (Web Push, playlist gallery, favorites export) are not repeated.

### 3.1 Shareable game recap page (low effort, high viral value)

The podium screen dies with the tab. Generate a public, read-only recap at `/{slug}/recap` once a session is `finished`: podium, per-track list (title/artist/who guessed), date, player count. All data already exists and is public-readable. This is the natural "share in the group chat afterwards" artifact — and today the app has zero post-game presence. Pairs well with the favorites button (recap = second chance to favorite).

### 3.2 "Rejouer" — clone a finished session (low effort)

One button on the recap/game-over screen: create a new session with the same tracks (fresh slug, tracks re-queued, `added_by` remapped or nulled for autonomous mode). The reset flow already proves the mechanics; this is reset-into-a-new-session. Immediate use case: the same playlist for the next group at a party, or replaying a public playlist game.

### 3.3 Speed-based scoring option (medium effort, big gameplay depth)

Per-buzz timings are already recorded (buzz `created` vs track `started_at`, server clock domain — the autonomous v1 shipped "per-buzz timings"). Add an optional scoring mode in session settings: full point for a correct buzz under N seconds, degressive after. Displays as "+0.8" style points on the solved overlay. This turns the leaderboard from binary to skill-graded and reuses data the app already captures. Requires generalizing the score from `solved_by`-derived counting to a stored per-track score — do it when touching scoring anyway for team mode (3.4).

### 3.4 Team mode (medium effort)

IRL parties naturally split into teams ("les vieux contre les jeunes"). Add `players.team` (nullable text/color chosen in the lobby), aggregate the existing ratio scoring per team, one buzz locks out the whole team on wrong answers. The equity and validator logic is unaffected (tracks stay per-player). Mostly lobby UI + a grouped ranking tab.

### 3.5 Big-screen / TV mode (medium effort, ideal for IRL)

A `/{slug}/tv` route: spectator view without a player record — current track status (no answer until reveal), buzz order as it happens, countdown, votes, ranking, session QR code in a corner. IRL games project this on a TV while phones stay the buzzers. Read-only (public data), so no security work needed; reuses `useTracks`/`useBuzzes`/`usePlayers` as-is. Also doubles as the "author of the playlist watches without playing" answer from the ROADMAP v2 notes.

### 3.6 Instant game from a theme (medium effort, depends on playlist gallery)

The wizard's autonomous path requires a prepared playlist. Add a "quick game" path: pick tags/decade → the app assembles a playlist from public `playlist_tracks` (and later, favorites marked shareable). Lowers the barrier from "someone prepared 20 tracks" to "we want to play now". Builds directly on the public-playlists gallery already planned for v2 — same query, different entry point.

### 3.7 Player career stats (low-medium effort, retention)

For logged-in users, a member-area "Stats" page: games played, guess ratio over time, best streak, most-guessed artists (via `videos.artist`), nemesis track types. All computable from existing `players.auth_user` + `tracks.solved_by` + `favorites`. Gives accounts a reason to exist beyond favorites — currently guests get 95 % of the product.

### 3.8 Playlist import from streaming services (higher effort, later)

Paste a Spotify/Deezer playlist link → server-side fetch of the track list (both have public oEmbed/API endpoints for public playlists) → match each "artist - title" through the existing search proxy → user confirms matches in the playlist editor. The YouTube-playlist import was removed in 2026-05 as unused, but the context changed: the playlist builder now exists, autonomous mode consumes playlists, and people's playlists live on streaming services, not YouTube. The matching UI is the same per-track confirm flow the editor already has.

### Explicitly not recommended

- **Native app / capacitor wrapper** — the PWA + Web Push plan already covers install and notifications; a store presence adds release friction for no gameplay gain.
- **In-app audio hosting** (uploading MP3s) — copyright exposure, storage cost, and YouTube coverage is near-total; the Invidious hardening in 2.5 is the better investment.
- **Global public leaderboards** — cross-session scores are not comparable (track difficulty varies wildly) and it invites the cheating that 2.1 exists to limit; keep competition per-session/per-group.
