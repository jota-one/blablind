## 1. Architecture overview

**Stack**: Astro 7 (Node SSR adapter, standalone) serving Vue 3 islands + PocketBase 0.26 backend (SQLite). Tailwind 4 / daisyUI / PrimeVue for UI. Build output goes into `pb/pb_public/` so PocketBase serves the frontend in production.

**Three SPAs** mounted as Astro islands, each with its own router:
- `src/game/` — the live game (the realtime core). Mounted on `/[slug]`.
- `src/admin/` — admin panel (users, roles, videos, settings).
- `src/client/` — authenticated member space (profile, my blindtests, game settings).

**Backend**: PocketBase collections via migrations in `pb/pb_migrations/`. Collections: `sessions`, `players`, `tracks`, `videos`, `buzzes`, `feedback`, `roles`, `users`, `app_settings`. One JSVM hook: `admin_user_verified.pb.js`.

**External integrations**:
- YouTube IFrame API (client) for playback — `YoutubePlayer.vue`.
- YouTube oembed (client fetch) for title/artist autofill.
- Invidious instances (server proxy `/proxy/search`) for track search, with 7-instance failover.

### Realtime model

Everything realtime rides on **PocketBase SSE subscriptions**. Each game composable opens its own subscription:

| Composable | Subscribes to | Reconnect recovery |
|---|---|---|
| `useSession` | `sessions/{id}` + `PB_CONNECT` | ✅ reloads on reconnect |
| `usePlayers` | `players` filtered by session + `PB_CONNECT` | ✅ reloads on reconnect |
| `useBuzzes` | `buzzes` filtered by track | ❌ **no PB_CONNECT recovery** |
| `useTracks` | `tracks` filtered by session | ❌ **no PB_CONNECT recovery** |

There is **no server-authoritative game loop**. All game-state transitions (advance track, validate buzz, mark solved, host election, skip resolution, orphan handling, duplicate flagging) are decided **client-side** and written back to PocketBase. Coordination between clients is by convention ("only the host does X", "only the track admin does Y"), guarded by computed booleans. This is the structural root of most fragility below.

### Player identity / presence

- A "player" row is created on join; its id is stored in `localStorage` (`blablind_player_{sessionId}`) plus a `secret` UUID.
- Presence = heartbeat: `App.vue` PATCHes `players.last_seen` every **15 s**; a player is "online" if `last_seen` < **30 s** old (`utils.isOnline`).
- `usePlayers` re-evaluates online status on a **5 s** clock tick.

## 2. Fragility catalog (ranked)

Severity: 🔴 high (causes visible bugs / state divergence) · 🟠 medium · 🟡 low / hardening.

### 🔴 F1 — Tracks & buzzes have no SSE-reconnect recovery
`useTracks.ts` and `useBuzzes.ts` subscribe but never re-`load()` on `PB_CONNECT`, unlike `useSession`/`usePlayers` which do. After **any** SSE drop (mobile backgrounding, wifi blip, server restart), missed `tracks`/`buzzes` events are lost forever and never reconciled. Result: a client keeps showing the old current track, a stale queue, or a missing buzz, while everyone else moved on. This is a prime "workflows stepping on each other" symptom.
- **Fix**: mirror the `pb.realtime.subscribe('PB_CONNECT', () => load())` pattern in both composables. For `useBuzzes`, reload the current track's buzzes.

### 🔴 F2 — Mobile background throttling drives presence flapping
Heartbeat 15 s, offline threshold 30 s → **two missed beats = offline**. Mobile browsers throttle/suspend `setInterval` for backgrounded tabs, so a player who locks their phone for 30 s is marked offline. Going offline cascades into several automatic workflows that then "step on each other":
- host re-election (F3),
- orphan-track host prompt (`nextOrphanOwner`, Room.vue:793),
- equity recompute (`canAddTrack`/`canDeleteTrack`),
- skip-threshold change (`skipVotesNeeded` shrinks → a pending skip can suddenly resolve).
- **Fix options**: widen threshold to ~45–60 s; send a heartbeat on `visibilitychange`/`focus`; debounce the offline→workflow transitions (require N seconds of confirmed-offline before acting).

### 🔴 F3 — Host election can flap between clients
`Room.vue:933-945`: every online client runs the election watcher and elects "earliest-created online player"; only the elected one writes `session.host`. This is deterministic **only if every client shares the exact same `onlinePlayers` set**. Because online-ness depends on each client's local clock + 5 s tick + 30 s threshold, two clients can legitimately disagree about who is online during the transition window and elect **different** hosts, producing write churn / host flip-flop. Combined with F2 this fires often.
- **Fix**: make election server-side (a PocketBase hook / cron picking host when the current host's `last_seen` is stale), or add hysteresis + a single "elector" (e.g. only the lowest-id online client may write).

### 🔴 F4 — `useTracks` re-fetches every event and can resurrect deleted tracks
`useTracks.ts:106-119`: on **every** create/update event the handler does an extra `getOne(..., expand:'video')`.
- **Performance**: a `shuffleAllTracks`/reset batch of N tracks emits N events × every client → N×getOne per client. With 20 tracks and 6 players that's 120 extra requests per shuffle.
- **Correctness**: the `create` branch awaits `getOne` then **unconditionally pushes**. If a `delete` for the same track arrives during that await, the track is re-added (zombie). Out-of-order async resolution also reorders pushes before `sort()`.
- **Fix**: the SSE event already carries the record; subscribe with `expand` in options (`{ expand: 'video' }`) instead of re-fetching, and guard the create push against concurrent deletes (check still-present / use a pending-delete set like `manuallyDeletingIds`).

### 🟠 F5 — Multiple independent timers can both advance the track
Track advancement is triggered from **three** places, each on its own `setTimeout(3000)`:
- `validateBuzz` (Room.vue:1207) — after correct answer,
- `solvedBuzz` watcher (Room.vue:875) — overlay,
- `skipVoteArray` watcher (Room.vue:1019-1055) — skip resolution.

When events interleave (e.g. host validates a buzz **and** skip votes cross the threshold within the same 3 s window), two timers can both call `finishTrack` + `playTrack`, double-advancing and skipping a track. The `isHost` / `animationState.type==='skipped'` guards reduce but don't eliminate the overlap.
- **Fix**: a single guarded transition function with an in-flight lock (e.g. `if (advancing) return; advancing = true`), or move advancement server-side.

### 🟠 F6 — Two clients can simultaneously believe they're the track admin
`trackValidatorId` (Room.vue:731-736) = the track owner if online, else the host. During the owner's online→offline transition window, the owner's client may still consider itself online while the host's client already sees the owner offline. Both then have `isCurrentTrackAdmin === true` and can both run admin-only actions:
- `validateBuzz` → **double score increment** (read-modify-write `score+1`, F7),
- `invalidateBuzz` (idempotent, harmless),
- auto-reject timer.
- **Fix**: derive validator authority from a single source (the host always arbitrates, or server-side), and make scoring atomic (F7).

### 🟠 F7 — Non-atomic score increment
`Room.vue:1204`: `score: (buzzer.score||0)+1` is a client-side read-modify-write. Concurrent validators (F6) or a stale `players` cache lose increments / double-count.
- **Fix**: PocketBase has no atomic increment in the JS SDK directly; do it in a collection hook (`record.set('score', record.get('score')+1)` server-side on buzz→correct), or recompute score from `tracks.solved_by` count (the leaderboard already derives ratios this way — score could be fully derived and not stored).

### 🟠 F8 — PB filter built from raw user/URL input (injection + fragility)
- `useSession.ts:13`: `getFirstListItem(\`slug="${slug}"\`)` where `slug` comes straight from `window.location.pathname`. A crafted slug with a `"` breaks/injects into the filter.
- `Room.vue:1285` (reset): `tracks.map(t => \`track="${t.id}"\`).join(' || ')` builds an unbounded OR filter — with many tracks this risks hitting filter/URL length limits and is O(n) fragile.
- **Fix**: use PocketBase filter params binding (`pb.filter('slug={:slug}', { slug })`). For reset, fetch buzzes per-track in batches or by `session` relation if available.

### 🟠 F9 — Imperative YouTube control fights the reactive `paused` prop
`paused` (Room.vue:64) = `audioUnlocked && (!!activeBuzz || pausedByDuration)`. `YoutubePlayer` watches it to pause/play. But `solvedBuzz` watcher (`playVideo()` + `seekTo`), `validateBuzz` (`playVideo()` via nextTick), and `isTrackSolvedAndPlaying` watcher (`seekTo`) also command the player imperatively. These can race: a `seekTo(reveal)` then an autoplay/pause toggle, or play+pause within the same tick. Symptom: occasional wrong-position playback or a track that briefly resumes the intro instead of the reveal section.
- **Fix**: funnel all playback intent through the `paused` + a `seekTarget` prop so the player is the single owner of imperative calls.

### 🟡 F10 — `findOrCreateVideo` race only partially handled
`useTracks.ts:23-48` catches the create-collision and re-queries — good. But two near-simultaneous adds of a new video still each call `getList` (miss) then `create`; the loser's catch re-queries. Acceptable, but relies on a unique constraint on `videos.video_id` to actually throw. Confirm the unique index exists, otherwise duplicates slip through silently.

### 🟡 F11 — Join host-assignment race
`App.vue:115-122`: on join, if no other active player, set self host. Two simultaneous first-joiners both see 0 active others → both claim host; last-write-wins, then F3's watcher reconciles. Usually self-heals but momentarily two hosts.

### 🟡 F12 — Pervasive `any` typing
Every PB record is `any` (`session`, `player`, `track`, `buzz`...). No generated/typed schema. This removes the compiler's ability to catch field renames, the exact class of bug that bites a fast-moving realtime app. Consider a typed PB schema (e.g. `pocketbase-typegen`) and typing the composables' refs.

### 🟡 F13 — Misc
- `usePlayer.ts` appears **dead/duplicated** by the richer restore logic in `App.vue` (`restorePlayer`). Confirm and delete to avoid two divergent join paths.
- `useBuzzes` create handler pushes without de-dup; a reconnect+reload combined with a late event could double-insert (mitigated today only because there's no reconnect reload — see F1, fixing F1 needs de-dup by id).
- Reset (`resetSession`) clears local timers but other clients' `duplicateCheckTimeout` keep running against now-reset tracks (3.5 s window) — could re-flag a duplicate right after reset.
- `animationState` from the `solvedBuzz` path never sets `.type` (Room.vue:879) so `SolvedOverlay :type` is `undefined`; verify the component handles that.
- Invidious search proxy has no caching and no per-client rate limiting; a popular search hammers public instances (and may get the instance blocked).

## 3. What's solid

- Reconnect recovery pattern (where present) is the right idea; just needs to cover all four subscriptions.
- Batch updates chunked at 45 ops (`batchUpdateOrders`, `resetSession`) respect PB's batch limit — good.
- Equity / shuffle interleaving logic is thoughtful (fractional-position interleave).
- `findOrCreateVideo` race handling and `manuallyDeletingIds` show awareness of the realtime pitfalls.
- i18n is fully externalized (en/fr), identifiers are English per project convention.

## 4. Recommended priority order

1. **F1** — add PB_CONNECT recovery to `useTracks` + `useBuzzes` (cheap, high impact).
2. **F2/F3** — presence hysteresis + server-side (or single-elector) host election.
3. **F4** — stop the per-event `getOne`, guard zombie re-adds.
4. **F5/F6/F7** — single locked transition function + server-side scoring (consider deriving score entirely from `solved_by`).
5. **F8** — parameterized filters.
6. Then hardening: F9–F13.

The throughline: **move authority off the clients.** Today every browser is a co-author of game state, coordinating by timing and presence guesses. Each fragile point above is a place where two clients briefly disagree and both write. A small amount of server-side arbitration (PocketBase hooks/cron for host election, scoring, and track advancement) would collapse most of this class of bug.
